linux 環境下將 Brave 完全關閉後重新開啟，進行**第一次搜尋時會卡死 10 秒至數十秒**；但只要不完全關閉瀏覽器，後續的所有搜尋都是瞬間秒開。

### 觸發時機與根本原因
此問題在透過 **SSH** 或 **Chrome Remote Desktop (CRD)** 等遠端桌面連線時極易被觸發。

1. **D-Bus 與金鑰庫死鎖**：Chromium 架構在冷啟動初始化時，預設會嘗試存取桌面環境的金鑰庫（`gnome-keyring` 或 `kwallet`）來加密本機密碼。
2. **遠端環境缺少授權工作階段**：在 CRD 建立的獨立虛擬顯示環境或 SSH 工作階段中，缺少標準本機登入的 PAM 解鎖環境，導致 D-Bus 請求直接掛起卡死。
3. **網路執行緒凍結**：Brave 在等待金鑰庫回應期間會同步凍結網路請求，直到逾時放棄才放行查詢。第一次逾時成功後，連線進入連線池保持運作（Keep-Alive），因此後續搜尋完全不卡。

---

## 🛠️ 修復方式（Fix）

核心修復方式為：**在啟動參數中加入 `--password-store=basic`，並透過建立軟連結接管執行命令。**

1. **加上 `--password-store=basic` 參數**：
   強制 Brave 使用純文字基本金鑰加密本機 Cookie，完全繞過系統 D-Bus 金鑰庫請求，徹底解決 CRD 與 SSH 等遠端環境下的冷啟動凍結問題（密碼若託管於 Bitwarden，此改動對安全性零影響）。

2. **重建符號連結（Symlink）**：
   在使用者路徑 `~/.local/bin` 下建立注入此參數的啟動腳本，並建立與 `brave`、`brave-browser-stable` 同名的軟連結。利用 Linux `PATH` 搜尋順序優先攔截呼叫，無論從終端機指令、CRD 遠端桌面捷徑皆能自動套用參數，且在瀏覽器軟體更新後依然持續生效。
